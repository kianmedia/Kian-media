# P1.1 — Close the queue-injection hole and make the shared enqueue helper idempotent

**why** — Highest-severity item that is fixable entirely in additive SQL. `docs/review_thread_email_RUNME.sql:40` grants `EXECUTE` on `nt_enqueue_email` to `authenticated`, so **any logged-in portal account** (client, employee, renter) can insert arbitrary `recipient_email` / `subject` / `body_text` rows that the cron will mail from the company's Apps Script identity — and, because the relay has a ~100/day Gmail ceiling, can trivially exhaust the quota and black out every portal notification. Separately, the same function writes `idempotency_key`, `event_id`, `notification_id` and `recipient_id` all NULL, so it defeats all three of `email_deliveries`' dedupe mechanisms simultaneously (`uq_edel_idem` is a *partial* index `where idempotency_key is not null`, `unique (event_id, recipient_id)` never fires on `(NULL,NULL)`, `notification_id unique` is NULL) — this is why a retried custody RPC re-mails.

**files**
- New `docs/email_backbone_phase1_enqueue_RUNME.sql`.
- `docs/NOTIFICATION_EVENT_CONTRACT.md` — document the new helper name under the existing enqueue section; do **not** change any event name or payload key.

# P1.2 — Worker delivery correctness: bound at-least-once, universal reaper, hard timeout

**why** — Four interacting defects mean a crashed or blipped send can neither complete nor die. `attempts` is written **only on a completed attempt** (`notifyWorker.ts:85`, `:105-109`), and the claim PATCH at `:71` doesn't touch it — so a lost success PATCH (`patchAsService` returns `ok:false` on network throw / non-2xx / zero rows per `lib/server/supabaseAdmin.ts:219-243`, and `:84` **discards that result** while `:88` still counts `out.sent++`) leaves the row `processing` with `attempts` unchanged. The reaper (`:160-161`) then returns it to `pending` **without burning an attempt**, so it can never reach `MAX_ATTEMPTS` and never dead-letters; it duplicates roughly once per daily cron for 7 days until the `created_at >= cutoff` filter (`:167`) silently strands it at `pending, attempts=0`, invisible to every health signal. The reaper also lives only in the generic branch — the exact-ID branch returns at `:148` first — so an event-bound row killed mid-send waits for the daily cron. And `projectNotify.ts:112` has no `AbortSignal`, so one hung Apps Script redirect can consume the whole function budget.

**files**
- `lib/server/notifyWorker.ts`
  - `:71` — claim PATCH becomes `{ status: "processing", attempts: (d.attempts ?? 0) + 1, next_attempt_at: leaseIso }`; drop the increment from the success PATCH `:85` and the failure PATCH `:106` (they now read the already-incremented value). A crashed in-flight row costs exactly one attempt.
  - `:84` — check the returned `AdminResult`; if `!ok`, do **not** `out.sent++` — record `out.retrying++` with `last_error: "sent_unconfirmed"` so the run reports what it actually persisted.
  - `:127` — hoist the two reaper PATCHes (`:160-161`) **above** the `if (opts.deliveryIds …)` branch so both paths reclaim expired leases. They are already idempotent and status-guarded; the cost is two bounded PATCHes on the immediate path.
  - Reaper burn: replace the bulk PATCH with `select id,attempts where status=processing and next_attempt_at < now`, then per-row PATCH `{ status: attempts+1 >= MAX_ATTEMPTS ? 'failed' : 'pending', attempts: attempts+1, last_error: 'reclaimed_stuck_processing', next_attempt_at: terminal ? null : now + 5*2^(attempts+1) min }`, reusing the exact terminal/backoff expressions from `:102-108`. Cap the select at 200 rows.
  - Export `RECOVERY_WINDOW_HOURS = 168` next to the constants at `:24-26`.
- `lib/server/projectNotify.ts:112` — add `signal: AbortSignal.timeout(20_000)`; the existing `catch` at `:141` already maps a throw to `network_error`, which is a normal burnable attempt.
- `app/api/integrations/project/notify-admin/route.ts:126-129` — import the exported `RECOVERY_WINDOW_HOURS` and use it in the **expire path only** (leave `BACKLOG_HOURS` governing `retry_one`'s age gate at `:190-191` and the previews). - `components/portal/projectcore/NotifyMonitor.tsx:76` — render the returned `window_hours` in the confirm dialog instead of the hardcoded `>24h` / `24 ساعة`.

**SQL** — none. The status vocabulary is unchanged: `failed` + `next_attempt_at is null` already *is* the dead-letter set, because the worker is its only writer.

**tests** — new `tests/email_worker_atleastonce_phase1.test.js`, following the mock-reimplementation style already used in `tests/email_queue_worker_9e.test.js:34`: simulate claim → crash → reap → claim, and assert `attempts` reaches `MAX_ATTEMPTS` and the row terminates as `failed` in ≤5 cycles (today it never terminates); assert the exact-ID branch reclaims an expired lease instead of returning `claim_conflict`; assert a `patchAsService` failure on the success PATCH does **not** increment `sent`; pin `AbortSignal.timeout` present in `projectNotify.ts`.

**risk — medium-low, and this is the one subphase to review hardest.** Moving the increment to claim time means a row that legitimately fails 5 transient times now dead-letters one cycle earlier than before — acceptable and intended. # P1.5 — Restore event attribution in the monitor and the trace

**why** — The canonical Batch-10 emitter never writes `event_id` (`global_notifications_core_batch10_RUNME.sql:73-74`; same at `event_bound_email_dispatch_batch9g_RUNME.sql:82` and `project_review_decouple_batch10_RUNME.sql:71`), while every monitor read joins through it (`9c:122,130,134`). So every row from the pipeline all modules are supposed to migrate onto lands under `'(none)'`/`unknown`, and the degradation gets *worse* as legacy `pc_event_emit` traffic ages out of the 30-day window. The worker compounds it: `SELECT_COLS` (`:55`) omits `correlation_id` and `traceRow` (`:57`) substitutes the always-NULL `event_id`, so `notification_trace` stamps `gen_random_uuid()` on every email leg (`notifications_e2e_repair_batch9d_RUNME.sql:104`) and correlation-based tracing is broken end-to-end. The event name **is** already on disk in every canonical row — `idempotency_key` is `<event>:<entity>:<user>` — it is simply never parsed.

**files**
