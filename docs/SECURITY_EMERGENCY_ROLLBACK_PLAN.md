# خطة التراجع الطارئ — الأمن والصلاحيات

> **لا تُنفَّذ الآن.** مرجع للاستخدام عند فشل مُثبَت أثناء التطبيق.
> القاعدة الحاكمة: **جرّب أضيق تدخّل أوّلًا.** أغلب المشاكل تُحلّ بزرّ الطوارئ وحده،
> بلا تراجع عن أيّ إصلاح أمنيّ.

---

## 0 · شجرة القرار — ابدأ من هنا

```
هل المشكلة أن أحدًا يُطالَب بـMFA ولا يستطيع تجاوزها؟
├─ نعم → زرّ الطوارئ فقط.  ⬇ §1 .  لا تتراجع عن شيء آخر.
└─ لا
   ├─ هل عملية إدارية تُرفض بـauthorization_denied وهي مشروعة؟ → §4 (Fix B)
   ├─ هل مستخدم فقد وصولًا كان لديه؟ → §5 ⚠️ غالبًا **ليس** عطلًا
   ├─ هل نموذج عامّ (عرض سعر/فرص) انكسر؟ → §5 فورًا
   └─ هل منح دور مشروع يُرفض؟ → §3 (Fix A)
```

---

## 1 · زرّ الطوارئ — الأداة الأولى دائمًا

```sql
update public.mfa_settings set enforcement_mode = 'off' where id = 1;
```

**متى:** أيّ مشكلة متعلّقة بـMFA — مطالبة غير متوقّعة، جهاز مفقود، شاشة عالقة،
عملية حسّاسة لا تكتمل.

**الأثر:** فوريّ على الطلب التالي. `mfa_write_ok()` يفحص الوضع **قبل كل شيء عدا
service_role**، فلا شيء يتجاوزه.

**ما لا يفعله:** **لا يُلغي** Fix A ولا Fix B ولا Fix C. تلك إصلاحات صلاحيات مستقلّة
عن MFA تمامًا، ولها ملفّات تراجع خاصّة.

**لماذا هو الأداة الأولى:** لا يمسّ تعريف أيّ دالّة، ويُعكَس بأمر واحد، ويعمل من محرّر SQL
في Supabase — مسار اعتماد **مستقلّ عن البوابة وعن Vercel**، فلا يمنعه إقفال في البوابة.

**العودة:**
```sql
update public.mfa_settings set enforcement_mode = 'enrollment' where id = 1;
```

## 2 · التراجع عن S4b وحده

**الملفّ:** `docs/mfa_write_gate_s4b_ROLLBACK.sql`

**متى:** إن ثبت أن ربط البوّابة نفسه يمنع عملًا مشروعًا حتى مع `off` — وهو مستبعد،
لأن `off` يُبطل البوّابة أصلًا. **جرّب §1 أوّلًا دائمًا.**

**ما يُفقَد:** الحماية بخطوتين على العمليات السبع. تبقى كل حراسة التفويض.

**ما يبقى — وهذا مقصود:** ✅ Fix A · ✅ Fix B · ✅ Fix C · ✅ s4pre
التراجع يُزيل **سطر البوّابة فقط** ويُبقي الأجسام بعد الإصلاح.

**هل نتراجع عن S4a أيضًا؟ ❌ لا.** بعد تراجع S4b لا أحد يستدعي `mfa_write_ok()`،
فتصبح خاملة تمامًا. إزالتها زيادة مخاطرة بلا فائدة.

## 3 · التراجع عن Fix A

**الملفّ:** `docs/authz_fixA_super_admin_grant_ROLLBACK.sql`

**متى:** إن منع الإصلاح منح دور **مشروعًا**. الحالة الوحيدة المتوقّعة: حساب يمرّ من
`can_manage_staff()` عبر `staff_role='super_admin'` (لا عبر `account_type='admin'`)
ويحتاج منح `super_admin`. **مع `super_admin_count = 0` هذه الحالة غير موجودة اليوم.**

> ⚠️ **الكلفة:** يعود أيّ super_admin قادرًا على صناعة super_admin آخر **بلا حدّ**،
> ولا سقف لعدد المُلّاك. الأفضل بكثير: امنح الدور **من حساب المالك** بدل التراجع.

---

## 4 · التراجع عن Fix B

**الملفّ:** `docs/authz_fixB_identity_permissions_ROLLBACK.sql`

**متى:** إن ثبت أن عمل تشغيليًّا مشروعًا كان يعتمد على قدرة **المدير** على تعديل
صلاحيات الموظفين.

> ⚠️ **الكلفة:** يعود أيّ مدير مشروع قادرًا على إعادة كتابة صلاحيات أيّ موظف،
> **وعلى إسناد نفسه** مهنة محمّلة بصلاحيات حسّاسة — تصعيد ذاتيّ دائم.

**الاعتماديّة العكسيّة:** ⛔ **لا تتراجع عن s4pre قبل Fix B.**
Fix B يستدعي `can_manage_identity()`؛ إزالتها أوّلًا تجعل الدوالّ السبع ترفع
`function does not exist` عند كل استدعاء ⇒ **تعطّل إدارة الصلاحيات كليًّا**.
الترتيب الصحيح: **Fix B ثم s4pre** (وغالبًا لا داعي لإزالة s4pre إطلاقًا — دالّتان خاملتان).

## 5 · Fix C — ⛔ لا تتراجع عنه

**الملفّ موجود** (`authz_fixC_null_failopen_gates_ROLLBACK.sql`) لكن **لا تستعمله**.

**لماذا:** التراجع يُعيد **الفشل-المفتوح**: مُسنِد يُعيد `NULL`، فـ`if not NULL` لا تتحقّق
أبدًا، والاستثناء لا يُرفع، وجسم `SECURITY DEFINER` يُنفَّذ **متجاوزًا RLS**.
هذا هو **نفس شكل الحادثة** التي جعلت متصلًا غير مُصادَق يقرأ بيانات شركة حقيقية.

**⚠️ أثر متوقَّع يُشبه العطل وليس عطلًا:**
مستخدم كان يمرّ بسبب `NULL` سيبدأ يُرفض. **هذا الإصلاح يعمل.**
الحلّ **امنحه الصلاحية صراحةً**، لا أن تُعيد فتح الباب للجميع.

**الاستثناء الوحيد الذي يستحقّ تراجعًا:** لو انكسر نموذج **عامّ** (طلب عرض سعر / فرص)
لزائر غير مُسجَّل. الملفّ صُمّم ألّا يفعل ذلك (لا يسحب `EXECUTE` من `anon`)، لكن إن حدث
فالأولوية للمسار العامّ — تراجع، وأبلغني فورًا، فهذا يعني أن تحليل المسار العامّ كان ناقصًا.

## 6 · org_admin

**الملفّ:** `docs/org_admin_migration_ROLLBACK.sql`

**يرفض العمل** إن كان أيّ حساب يحمل الدور — تضييق القيد تحت صفّ حيّ **يُبطل القيد**
ويكسر كل `UPDATE` لاحق على `profiles`. أزِل الدور عن الحسابات أوّلًا بقرار واعٍ.

**يُبقي عمدًا** المُسنِدات الأربعة الجديدة: لا شيء يستدعيها، وحذفها أخطر من إبقائها.

## 7 · ترتيب التراجع الكامل — إن لزم كلّه

```
1. enforcement_mode = 'off'                    ← أوقف النزيف أوّلًا
2. mfa_write_gate_s4b_ROLLBACK.sql             ← أزل البوّابة
3. (S4a: اتركه — خامل)
4. authz_fixB_identity_permissions_ROLLBACK.sql
5. (s4pre: اتركه — خامل. ولا تُزله قبل 4)
6. authz_fixA_super_admin_grant_ROLLBACK.sql   ← فقط عند ضرورة مثبتة
7. Fix C: لا تتراجع
```

**اعكس ترتيب التطبيق دائمًا.** الملفّ الذي طُبّق أخيرًا يُتراجَع أوّلًا.

## 8 · منع التراجع الجزئي

**الخطر:** التراجع عن Fix B مع بقاء S4b ⇒ الدوالّ السبع تحمل بوّابة MFA لكن بلا
حراسة الهويّة ⇒ حالة **لم تُختبر قطّ**.

**القاعدة:** لا تتراجع عن طبقة **تحت** طبقة مُطبَّقة فوقها.
S4b يعلو Fix B يعلو s4pre. تراجع من الأعلى للأسفل، بلا قفز.

**تحقّق بعد كل خطوة تراجع:** شغّل القسم المقابل من
`docs/SECURITY_POST_APPLY_VERIFICATION.sql` وتأكّد أن الطبقات الباقية سليمة.

## 9 · فشل ملفّ في منتصف الترتيب

**كل ملفّ في الحزمة `begin … commit`.** الفشل يعني **تراجعًا ذاتيًّا كاملًا** —
لا حالة جزئية، ولا حاجة لتنظيف يدويّ.

**عند ظهور `raise exception 'فشل: …'`:**
1. **لا تُشغّل الملفّ مرّة أخرى** — الرسالة تقول ما الذي لم يتحقّق.
2. المعاملة تراجعت؛ قاعدة البيانات **كما كانت قبل الملفّ تمامًا**.
3. شغّل قسم التحقّق للمرحلة **السابقة** للتأكّد أنها ما زالت سليمة.
4. أبلغني بنصّ الرسالة حرفيًا.

**الاستثناء الوحيد:** `org_admin_migration` يُنفّذ `alter table … drop/add constraint`.
لو فشل **بين** الإسقاط والإضافة لبقي الجدول بلا قيد `staff_role`. الملفّ داخل معاملة
فهذا لا يحدث — لكن إن رأيت سلوكًا غريبًا بعد فشله، تحقّق:
```sql
select conname, pg_get_constraintdef(oid) from pg_constraint
 where conrelid = 'public.profiles'::regclass and contype = 'c';
```
