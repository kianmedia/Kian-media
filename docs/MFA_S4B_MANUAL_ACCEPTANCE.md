# S4b — نصّ قبول يدويّ على الإنتاج (المالك فقط)

> **الغرض:** إثبات أنّ بوّابة الكتابة الحسّاسة تعمل **في قاعدة البيانات** لا في الواجهة،
> وأنّها **لا تقفل أحدًا**، وأنّ زرّ الطوارئ يعمل فورًا.
> **مدّة التنفيذ:** ٢٥–٣٥ دقيقة · **يُنفَّذ على الإنتاج** · **كل خطوة قابلة للتراجع**.

هذا ليس اختبارًا للواجهة. ثلاثة اختبارات من العشرة (T‑1، T‑6، T‑8، T‑10) تتجاوز الواجهة
عمدًا وتضرب PostgREST مباشرة، لأنّ بوّابة تعمل في الواجهة فقط ليست بوّابة.

---

## ٠ · قبل البدء — شروط لا تُتجاوز

| # | الشرط | كيف تتأكّد |
|---|---|---|
| 0.1 | SQL مُطبَّق بالترتيب: `fixA` → `fixC` → `s4pre` → `fixB` → `s4a` → `s4b` | كل ملفّ يطبع `✓` في نهايته؛ إن لم يطبع فلم يكتمل |
| 0.2 | `enforcement_mode = 'enrollment'` | `select enforcement_mode from public.mfa_settings where id = 1;` |
| 0.3 | حسابك (المالك الأوّل) يملك عامل TOTP **مُفعَّلًا** | البوابة ← الأمان ← يظهر العامل بحالة «مُفعَّل» |
| 0.4 | حساب المالك الثاني **لا يملك** أيّ عامل | مقصود — هو مادّة اختبار T‑8 |
| 0.5 | حساب موظّف وحساب عميل جاهزان للدخول | مادّة اختبار T‑9 |
| 0.6 | تبويب SQL Editor مفتوح على مشروع الإنتاج | تحتاجه في T‑10 خلال ثوانٍ |

**بطاقة الطوارئ — اطبعها أو ضعها في تبويب جاهز قبل أن تبدأ:**

```sql
update public.mfa_settings set enforcement_mode = 'off' where id = 1;
```

سطر واحد. يُلغي البوّابة كلّها فورًا وبلا إعادة تسجيل دخول. لا يمسّ الأدوار ولا الصلاحيات
ولا العوامل المسجّلة. **إن ارتبك أيّ اختبار — شغّله أوّلًا ثم اسأل.**

**⚠️ تنبيه واحد:** في T‑6 ستنسخ رمز جلستك (`access_token`). هو مفتاح دخول كامل.
استعمله في نافذة الطرفية عندك فقط، ولا تلصقه في محادثة ولا رسالة ولا ملفّ.

## T‑1 · المنع عند aal1 — البوّابة موجودة أصلًا

**ما تفعله:**
1. سجّل الخروج ثم الدخول بحساب المالك الأوّل بكلمة المرور **فقط**.
   إن ظهرت نافذة التحقّق عند الدخول، أكملها ثم **سجّل الخروج وادخل مجددًا** — نحتاج جلسة `aal1` نظيفة.
2. تأكّد أنّ الجلسة `aal1` فعلًا: في SQL Editor **لا يصلح** (هناك أنت `service_role`).
   بدلًا من ذلك افتح البوابة ← الأمان، ويجب أن يظهر مستوى الجلسة `aal1`.
3. اذهب إلى: البوابة ← الموظفون ← اختر موظفًا **غير محميّ** ← غيّر «صلاحية النظام» إلى دور آخر.

**ما تتوقّعه:**
- نافذة **«تأكيد الهوية / Confirm it's you»** تظهر فورًا.
- الدور في القائمة **لم يتغيّر** خلفها.
- **لا** رسالة خام مثل `mfa_required`، و**لا** شاشة فارغة، و**لا** رسالة «تم الحفظ ✓».

**ما يُثبته:** البوّابة مربوطة فعلًا بالدالّة الحيّة (وليست بتعريف مهجور)، والواجهة
تُترجم `P0002` إلى فعل مفهوم بدل نصّ تقنيّ. لو ظهر نصّ `mfa_required` خامًّا فالغلاف
غير مربوط في تلك الشاشة — عطل واجهة، لا عطل بوّابة.

---

## T‑2 · الترقية — النافذة تقبل الرمز

**ما تفعله:** في النافذة نفسها من T‑1، أدخل الرمز السداسيّ الحالي من تطبيق المصادقة واضغط «تأكيد».

**ما تتوقّعه:**
- تُغلق النافذة خلال ثانية أو ثانيتين.
- **إن أدخلت رمزًا خاطئًا عمدًا أوّلًا:** تبقى النافذة مفتوحة وتظهر
  «الرمز غير صحيح…/ That code is not correct…» — ولا تُغلق ولا تُنفَّذ العملية.

**ما يُثبته:** مسار التحقّق حيّ على الإنتاج، ورسالة الرمز الخاطئ مميَّزة عن رسالة
انتهاء الصلاحية (كانت هذه بالضبط نقطة الفشل في S3.5).

---

## T‑3 · النجاح بعد aal2 — الإعادة تحدث تلقائيًّا مرة واحدة

**ما تفعله:** لا شيء. راقب الشاشة بعد إغلاق النافذة مباشرة.

**ما تتوقّعه:**
- رسالة **«تم تحديث الدور ✓ / Role updated ✓»** — أي **نتيجة العملية الأصلية**.
- **لا** رسالة تقول «تم التحقّق بنجاح» وحدها ثم تتركك تضغط الزرّ ثانية.
- **لا** نافذة تحقّق ثانية.

**ما يُثبته:** الغلاف أعاد النداء الأصلي مرة واحدة بعد تأكيد `is_aal2` من Postgres،
وأبلغ نتيجة العملية لا نتيجة التحقّق. هذا هو الفرق بين «MFA نجح» و«الدور تغيّر».

---

## T‑4 · العملية نُفِّذت فعلًا — لا نجاح كاذب

**ما تفعله:**
1. اضغط **إعادة تحميل الصفحة** (F5) — لا تعتمد على ما في الذاكرة.
2. تحقّق أنّ الدور الجديد ما زال ظاهرًا.
3. تأكيد مستقلّ من قاعدة البيانات:
```sql
select id, full_name, staff_role, updated_at
from public.profiles
where id = '<ضع معرّف الموظف هنا>';
```

**ما تتوقّعه:** الدور الجديد في **الثلاثة** المواضع (الشاشة قبل التحديث، وبعده، وفي الجدول).

**ما يُثبته:** الكتابة التزمت (committed) ولم تُلغَ المعاملة. مهمّ لأنّ `mfa_require_aal2`
تُطلق استثناءً — واستثناء في منتصف دالّة كان قد يُلغي كتابات سابقة. هنا لا كتابة قبل
البوّابة أصلًا، وهذا الاختبار يُثبته عمليًّا.

---

## T‑5 · بعد إعادة التحميل — الترقية باقية ولا تُطلب في كل نقرة

**ما تفعله:**
1. أعد تحميل الصفحة (F5) — **لا تسجّل خروجًا**.
2. نفّذ كتابة حسّاسة ثانية: البوابة ← المهن والصلاحيات ← افتح «⚙ الصلاحيات» لمهنة ← بدّل أيّ صلاحية غير حسّاسة.

**ما تتوقّعه:**
- **لا** نافذة تحقّق.
- الصلاحية تُحفظ مباشرة، ورسالة «✓ حُفظ وتأكّد من الخادم».

**ما يُثبته:** رمز `aal2` كُتب في مخزن الجلسة الواحد (`saveSession`) لا في متغيّر مؤقّت،
فبقي بعد إعادة التحميل. لو طُلبت النافذة مجددًا هنا، فالرمز المرقّى لم يُحفظ — وهو
عطل ثبت حدوثه قبل إصلاح S3.5، ويجب ألّا يعود.

> ملاحظة: مدّة بقاء `aal2` هي مدّة رمز الوصول (ساعة افتراضيًّا). طلب النافذة بعد ساعة
> أو أكثر **سلوك صحيح** لا عطل.

---

## T‑6 · النداء المباشر لا يتجاوز البوّابة ★ الاختبار الحاسم ★

هذا هو الاختبار الوحيد الذي يُثبت أنّ الحماية في القاعدة لا في المتصفّح.

**ما تفعله:**
1. سجّل الخروج ثم الدخول بكلمة المرور فقط (جلسة `aal1` نظيفة — كما في T‑1).
2. في المتصفّح: `F12` ← Console ← نفّذ:
   ```js
   JSON.parse(localStorage.getItem(Object.keys(localStorage).find(k => k.includes('portal') || k.includes('session')))).access_token
   ```
   انسخ النصّ الناتج (هذا رمز جلستك — **لا تشاركه**).
3. في الطرفية:
```bash
ACCESS_TOKEN='<الرمز>'
ANON_KEY='<NEXT_PUBLIC_SUPABASE_ANON_KEY من Vercel>'
PROJECT='https://<مشروعك>.supabase.co'

curl -s -o /dev/stderr -w '\nHTTP %{http_code}\n' \
  -X POST "$PROJECT/rest/v1/rpc/admin_set_employee_override" \
  -H "apikey: $ANON_KEY" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"p_user":"<معرّف موظّف>","p_key":"finance.view_invoices","p_effect":"allow"}'
```

**ما تتوقّعه:** جسم فيه `"code":"P0002"` و`"message":"mfa_required"` — والأهمّ:
**لا صفّ في `employee_permission_overrides`.** تأكّد:
```sql
select count(*) from public.employee_permission_overrides
where user_id = '<معرّف الموظّف>' ;   -- يجب أن يبقى كما كان قبل الأمر
```

**ما يُثبته:** لا يمكن تجاوز البوّابة بتعطيل JavaScript، ولا بـcurl، ولا بأداة API، ولا
بلصق نداء في الـConsole. الحدّ هو `mfa_write_ok()` داخل Postgres. **لو نجح هذا النداء
وأُنشئ الصفّ، فالبوّابة غير مربوطة بهذه الدالّة — أوقف القبول فورًا.**

> رمز HTTP هنا `500` وليس `403`. هذا **متوقَّع**: PostgREST يُعيد 500 لصنف `P0` كلّه.
> الحكم يكون على `code`/`message` في الجسم لا على رقم HTTP — ولهذا لا يعتمد كود الواجهة على الرقم.

## T‑7 · الإلغاء — لا تنفيذ، ولا فقدان لما كتبته

**ما تفعله:**
1. بجلسة `aal1` نظيفة، افتح: البوابة ← المهن والصلاحيات ← تبويب المهن.
2. اكتب اسم مهنة جديدة بالعربية **والإنجليزية** ومفتاحًا، ثم اضغط «+ إضافة المهنة».
3. حين تظهر نافذة التحقّق، اضغط **«إلغاء»**.

**ما تتوقّعه:**
- رسالة صريحة: **«أُلغي التحقّق، ولذلك لم تُنفَّذ العملية. بياناتك كما هي.»**
- **الحقول الثلاثة ما زالت مملوءة بما كتبته** — لم تُفرَّغ.
- المهنة **لم** تُضف: أعد تحميل الصفحة وتأكّد أنّها غير موجودة.
- **لا** شاشة فارغة، ولا رسالة نجاح، ولا صمت.

**ما يُثبته:** ثلاثة أشياء معًا — الإلغاء يعني عدم التنفيذ؛ عدم التنفيذ **يُبلَّغ** ولا
يُترك للمستخدم ليخمّنه؛ وعمل المستخدم لا يضيع فيضطرّ لإعادة الكتابة. (الغلاف يستقبل
دالّة تُغلِّف حالة النموذج، والنافذة طبقة فوقية لا تُفكّك الشاشة.)

## T‑8 · إداريّ بلا عامل — لا يُقفل ★ الثابت المانع للإقفال ★

**ما تفعله:**
1. سجّل الدخول بحساب **المالك الثاني** (الذي لا يملك عامل TOTP — شرط 0.4).
2. نفّذ كتابة حسّاسة: غيّر دور موظّف غير محميّ، أو بدّل صلاحية مهنة.

**ما تتوقّعه:**
- العملية تنجح **مباشرة**.
- **لا** نافذة تحقّق إطلاقًا.
- رسالة النجاح الطبيعية.

**ما يُثبته:** الشرط (5) في `mfa_write_ok()`: لا يُمنع أحد إلّا إن كان **هو نفسه** يملك
عاملًا مُفعَّلًا. هذه خاصّية بنيوية لا سياسة — تعني أنّ رفع الوضع إلى `enrollment` لا
يمكن أن يقفل حسابًا لم يسجّل بعد. **لو ظهرت نافذة تحقّق هنا لحساب بلا عامل، فهذا خطر
إقفال — أوقف القبول وشغّل بطاقة الطوارئ.**

---

## T‑9 · الموظّف والعميل — خارج النطاق تمامًا

**ما تفعله:**
1. سجّل الدخول بحساب **موظّف**. حدّث حالة مهمّة، ارفع ملفًّا، اكتب تعليقًا.
2. سجّل الخروج، وادخل بحساب **عميل**. افتح مشروعًا، اعتمد مخرجًا أو اطلب تعديلًا، أرسل رسالة.

**ما تتوقّعه:** كل شيء كما كان قبل S4b. **لا** نافذة تحقّق في أيّ خطوة. لا رسالة جديدة.
لا تباطؤ ملحوظ.

**ما يُثبته:** الشرط (4) في `mfa_write_ok()` يحصر النطاق في
`account_type='admin'` أو `staff_role='super_admin'`. الموظّف والعميل لا يُبوَّبان حتى لو
سجّل أحدهم عامل TOTP من تلقاء نفسه. هذا يمنع أثرًا جانبيًّا على العمل اليوميّ — وهو
السبب الأوّل الذي يجعل فرق العمل تُطالب بإلغاء MFA بعد يومين.

---

## T‑10 · زرّ الطوارئ — يعمل فورًا وبلا إعادة دخول

**ما تفعله:**
1. عد إلى حساب المالك الأوّل بجلسة `aal1` نظيفة (خروج ثم دخول بكلمة المرور فقط).
2. ابدأ كتابة حسّاسة وتأكّد أنّ نافذة التحقّق تظهر — ثم **ألغِ**.
3. في SQL Editor:
```sql
update public.mfa_settings set enforcement_mode = 'off' where id = 1;
```
4. **بلا إعادة تحميل وبلا تسجيل خروج**، أعد نفس العملية مباشرة.

**ما تتوقّعه:**
- العملية تنجح **فورًا**، بلا أيّ نافذة.
- لا حاجة لرمز جديد ولا لجلسة جديدة.

**ثم أعِد الوضع:**
```sql
update public.mfa_settings set enforcement_mode = 'enrollment' where id = 1;
```
وأعد نفس العملية مرّة ثالثة — يجب أن **تعود** النافذة فورًا.

**ما يُثبته:** الشرط (2) في `mfa_write_ok()` يُقرأ من الجدول عند **كل نداء**، لا عند
تسجيل الدخول ولا عند إصدار الرمز. أي أنّ التراجع لا يحتاج نشرًا ولا ترحيلًا ولا
إخراج أحد. هذا هو ما يجعل تفعيل البوّابة قرارًا قابلًا للتراجع خلال عشر ثوانٍ —
وهو شرط تشغيله على الإنتاج أصلًا.

## متى تُوقف وتشغّل بطاقة الطوارئ — بلا تردّد

| العَرَض | المعنى |
|---|---|
| نافذة تحقّق لحساب **بلا** عامل مسجّل (T‑8) | خطر إقفال — الشرط (5) لا يعمل |
| نافذة تحقّق لموظّف أو عميل (T‑9) | البوّابة تجاوزت نطاقها |
| `curl` في T‑6 **نجح** وأُنشئ الصفّ | البوّابة غير مربوطة بالدالّة الحيّة |
| نافذة تحقّق ثانية بعد نجاح الأولى | حلقة — الغلاف لم يمنعها |
| شاشة بيضاء أو صمت بعد ضغط زرّ حسّاس | ابتلاع خطأ في مسار لم يُغلَّف |
| نصّ `mfa_required` خام على الشاشة | شاشة لم تُربط بالغلاف (عطل واجهة، البوّابة سليمة) |

```sql
update public.mfa_settings set enforcement_mode = 'off' where id = 1;
```

## ما لا يشمله هذا القبول — بصراحة

- **الاستعادة عند فقدان الجهاز.** لا يوجد مسار ذاتيّ. من يفقد هاتفه يحتاج إزالة العامل
  من لوحة Supabase يدويًّا. اختبرها **مرّة** على حساب تجريبي قبل أن تحتاجها فعلًا.
- **`mfa_admin_set_mode` غير مبوَّبة عمدًا.** لو بُوِّبت لصار زرّ الطوارئ نفسه خلف
  البوّابة التي يفتحها. تبقى على `is_owner()` وحدها.
- **دوال الخادم و`service_role`** (الكرون، الويبهوكات، مسارات `/api`) تمرّ بلا بوّابة —
  الشرط (1). هذا مقصود؛ لا رمز خدمة يحمل ادّعاء `aal` إطلاقًا.
- **القيمة `'enforced'`** ليست قيمة مشروعة في قيد قاعدة البيانات. لا تحاول ضبطها.
