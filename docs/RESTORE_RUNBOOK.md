# RESTORE_RUNBOOK — استعادة قاعدة البيانات

> **Wave 0 · V2-0.4-B** · الهدف: **RTO ≤ ٦٠ دقيقة**
> مرافق: `.github/workflows/db-backup.yml`

## ⚠️ اقرأ أولًا

**قبل Wave 0 لم يكن هناك نسخ احتياطي على الإطلاق** — لا سكربت ولا وجهة ولا إجراء.
Wave 0 أنشأت **الآلية**. لا تُصبح نسخًا احتياطيًا حقيقيًا إلا بعد:
1. ضبط سرّ `SUPABASE_DB_URL` في GitHub، **و**
2. تشغيل ناجح واحد على الأقل، **و**
3. **تمرين استعادة واحد على Preview.**

🔴 **نسخة لم تُستعَد مرة واحدة ليست نسخة احتياطية — هي ملف.**

## ١. تجهيز الأسرار (خطوة خالد)

GitHub → Settings → Secrets and variables → **Actions**:

| السرّ | إلزامي؟ | من أين |
|---|---|---|
| `SUPABASE_DB_URL` | ✅ | Supabase → Project Settings → Database → Connection string (URI) |
| `BACKUP_S3_BUCKET` | موصى به | وجهة خارج GitHub |
| `BACKUP_S3_ACCESS_KEY_ID` / `BACKUP_S3_SECRET_ACCESS_KEY` / `BACKUP_S3_REGION` | مع السابق | — |

❌ **لا تلصق أي قيمة في مستند أو رسالة.** الحالة تُذكر بالاسم فقط: `Configured` / `Missing` / `Unknown`.

## ٢. تشغيل نسخة

**يدويًا:** GitHub → Actions → **DB Backup** → Run workflow → اختر `preview` أو `production`.

**جدولة ليلية** (بعد ضبط الأسرار وتمرين استعادة ناجح): أزِل التعليق عن كتلة
`schedule` في ملف الـworkflow. 🔒 **G8: هذه GitHub Actions لا Vercel cron —
❌ لا تُضَف مهمّة Vercel رابعة.**

**فحوص السلامة المدمجة:** الوظيفة تفشل عمدًا إذا كان الملف < ٥٠KB أو كان فهرس
الأرشيف < ٥٠ عنصرًا. **الفشل الصاخب الآن أفضل من اكتشاف نسخة فارغة يوم الحاجة.**

## ٣. الاستعادة — الإجراء (هدف ≤ ٦٠ دقيقة)

> ⛔ **تمرَّن على Preview أولًا. لا تستعِد على الإنتاج إلا بقرار خالد الصريح.**

| # | الخطوة | الزمن |
|---|---|---|
| ١ | **قرّر النطاق:** جدول واحد أم القاعدة كاملة؟ استعادة جدول أسرع بكثير | ٥ د |
| ٢ | نزّل الـartifact من GitHub Actions (أو من التخزين الخارجي) | ٥ د |
| ٣ | تحقّق أنه قابل للقراءة: `pg_restore --list <file>` | ٢ د |
| ٤ | 🔴 **خذ نسخة من الحالة الحالية قبل الكتابة فوقها** — الاستعادة فوق حالة تالفة بلا نسخة تُفقد الدليل | ١٠ د |
| ٥ | استعِد (أدناه) | ١٠–٢٥ د |
| ٦ | تحقّق: `POSTCHECK` + عدّ صفوف الجداول الحرجة | ١٠ د |
| ٧ | أعِد نشر Vercel لتفريغ ذاكرة مخطط PostgREST | ٣ د |

### جدول واحد (الحالة الشائعة)
```bash
pg_restore --data-only --table=<table> \
  --no-owner --no-privileges \
  --dbname "$TARGET_DB_URL" kian-<env>-<stamp>.dump
```

### القاعدة كاملة
```bash
pg_restore --clean --if-exists \
  --no-owner --no-privileges \
  --schema=public \
  --dbname "$TARGET_DB_URL" kian-<env>-<stamp>.dump
```
⚠️ `--clean` **يحذف الكائنات القائمة قبل إعادة إنشائها**. لا تُشغَّل على الإنتاج بلا الخطوة (٤).

### بعد الاستعادة
```sql
-- أعمدة الموافقة (إن كانت الترحيلة مطبَّقة وقت النسخة)
select count(*) from public.public_intake where consent_given is true;
-- سلامة الصلاحيات المالية
select has_column_privilege('authenticated','public.project_core','budget_amount','SELECT');
```
ثم شغّل ملفات `*_POSTCHECK.sql` ذات الصلة.

## ٤. ما لا تغطّيه هذه النسخة

| غير مشمول | لماذا | البديل |
|---|---|---|
| ملفات Storage (صور العهدة · أدلة التأجير · المخرجات) | `pg_dump` يأخذ القاعدة لا الكائنات | 🔴 **فجوة مفتوحة** — تحتاج موجة لاحقة |
| `auth.users` | خارج `--schema=public`؛ مُدار من Supabase | استعادة Supabase المدمجة |
| الأدوار والصلاحيات | `--no-owner --no-privileges` | تُعاد بتشغيل حزم `authz_*` |
| متغيّرات Vercel | ليست في القاعدة | `.env.example` + `docs/ENVIRONMENTS.md` |

## ٥. تمرين الاستعادة — إلزامي مرة واحدة على الأقل

4. **سجّل الزمن الفعلي.** إن تجاوز ٦٠ دقيقة فهدف RTO غير محقَّق ويحتاج مراجعة.
