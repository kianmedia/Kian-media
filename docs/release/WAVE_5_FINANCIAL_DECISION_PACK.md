## ١. Revenue Source of Truth

| | |
|---|---|
| **Option A** | `fin_revenue` — جدول الاعتراف بالإيراد (`recognized_on` · `amount_net` · `amount_gross` · `zoho_reference`) |
| **Option B** | `fin_receivables` — المستحقّات (`issue_date` · `due_date` · مبالغ) |
| **Option C** | Zoho — ⛔ **ولا جدول فواتير Zoho في القاعدة**؛ المتاح **مزامنة** لا تخزين |

**البيانات:** §١ و§٦ من حزمة التحقّق (عدد الصفوف · تغطية `zoho_reference`).

| | A · `fin_revenue` | B · `fin_receivables` | C · Zoho |
|---|---|---|---|
| **المميزات** | يمثّل **الاعتراف** المحاسبيّ · له تاريخ اعتراف صريح | يمثّل ما **يُنتظر تحصيله** · أقرب لواقع النقد | مصدر الحقيقة التجاريّة الفعليّ |
| **المخاطر** | قد يسبق التحصيل فيُظهر إيرادًا لم يُقبض | ليس اعترافًا محاسبيًّا · فاتورة ملغاة تبقى | 🔴 **غير مخزَّن هنا** ⇒ القاعدة عمياء بلا اتصال |
| **الأثر على النظام** | يقرأ `fin_revenue` مباشرةً | يغيّر معنى «الإيراد» في كل تقرير | يفرض اعتمادًا حيًّا على تكامل خارجيّ |
| **الأثر على الأرقام التاريخية** | 🟢 لا شيء — الصفوف قائمة | 🟡 أرقام تاريخية تتغيّر معانيها | 🔴 قد تختفي أرقام لا مقابل لها في Zoho |
| **الأثر على Zoho** | يبقى تكاملًا | يبقى تكاملًا | يصير **اعتمادًا حرجًا** |
| **الأثر على التقارير** | متّسق مع المحاسبة | متّسق مع التدفّق النقديّ | يعتمد على صحّة المزامنة |
| **Migration required?** | ❌ لا | ⚠️ إعادة تفسير لا ترحيل | 🔴 نعم — يلزم تخزين |
| **Production verification?** | 🔴 نعم (§١) | 🔴 نعم | 🔴 نعم (§٦) |

**التوصية المحافظة: Option A — `fin_revenue`.**
**ولماذا محافظة لا تخمين:** لأنّها **الخيار الوحيد الذي لا يغيّر معنى رقم
تاريخيّ ولا يُدخل اعتمادًا خارجيًّا**. ⛔ وهي ليست حكمًا بأنّها الأصحّ محاسبيًّا
— قد يكون B أصحّ لغرض التدفّق النقديّ. **القرار قرارك.**

## ٢. Cost Source of Truth — 🔴 **الأخطر**

| | |
|---|---|
| **Option A** | `fin_costs` (`amount_net` · `vat_amount` · `amount_gross` · `supplier_id` · `incurred_on` · `source_kind`) |
| **Option B** | `project_expenses` (`amount_excl_vat` · `vat_amount` · `amount_incl_vat` · `recoverable_vat` · `phase` · `shoot_session_id`) |

**البيانات:** §١-ب (المشاريع المزدوجة و`delta`) و§٥ (التكرار عبر النطاقين).

| | A · `fin_costs` | B · `project_expenses` |
|---|---|---|
| **المميزات** | دورة مالية كاملة (مورّد · مركز تكلفة · ميزانية · اعتماد) | أقرب للإنتاج (مرحلة · جلسة تصوير) · يحمل `recoverable_vat` |
| **المخاطر** | أبعد عن واقع التصوير | ⛔ لا مورّد ولا اعتماد ولا مركز تكلفة |
| **الأثر على النظام** | التقارير المالية تقرأ نطاقًا واحدًا | يفصل التكلفة التشغيلية عن الدورة المالية |
| **الأثر على الأرقام التاريخية** | 🔴 **صفوف `project_expenses` تسقط من الحساب** | 🔴 **وصفوف `fin_costs` تسقط** |
| **الأثر على Zoho** | 🟢 محدود | 🟢 محدود |
| **Migration required?** | ⚠️ **مشروط بنتيجة §١-ب** | ⚠️ نفسه |
| **Production verification?** | 🔴 **نعم — إلزاميّ** | 🔴 نعم |

🔴 **وهذا القرار وحده قد يغيّر كل رقم تكلفة تاريخيّ**، لأنّ أيّ صفّ في النطاق
غير المختار **يختفي** من التقارير. ⛔ **ولا يجوز جمع النطاقين** — يضاعف الرقم،
و`assertSingleCostSource` في العقد يمنعه.

**التوصية المحافظة: Option A — `fin_costs`.**
**ولماذا:** لأنّها **لا تُسقط ضوابط** (مورّد · اعتماد · مركز تكلفة)، وإسقاط ضابط
أصعب استرجاعًا من إسقاط حقل وصفيّ. ⚠️ **مشروطة بأن يُظهر §١-ب أنّ التداخل صغير.**
ولو ظهر تداخل واسع بقيم مختلفة، فالقرار **ليس اختيار مصدر بل مشروع مصالحة**.

## ٣. Invoice Source of Truth

| | |
|---|---|
| **Option A** | Zoho — الفاتورة الرسمية الصادرة للعميل |
| **Option B** | `fin_receivables` (`doc_no` · `issue_date` · `due_date`) |

| | A · Zoho | B · `fin_receivables` |
|---|---|---|
| **المميزات** | 🟢 **هي الوثيقة الرسمية فعلًا** — وما يراه العميل والزكاة والضريبة | مخزَّن محلّيًّا ومتاح دائمًا |
| **المخاطر** | 🔴 **غير مخزَّن في القاعدة** ⇒ لا رقم رسميّ محلّيًّا | 🔴 قد لا يطابق الرقم الرسميّ ⇒ **مستندان متعارضان** |
| **Migration required?** | 🔴 نعم — تخزين مرجع الفاتورة على الأقلّ | ❌ لا |
| **Production verification?** | 🔴 نعم (§٦ — تغطية `zoho_reference`) | 🔴 نعم |

**التوصية المحافظة: Option A — Zoho** *مرجعًا رسميًّا*، مع تخزين **المرجع** لا
إعادة بناء الفاتورة.
**ولماذا:** لأنّ الفاتورة الرسمية **حقيقة خارجية** لا تُعاد صياغتها داخليًّا؛
وإعلان `fin_receivables` رسميًّا يخلق مستندين قد يتعارضان أمام جهة نظامية.

## ٤. VAT Source of Truth

| | |
|---|---|
| **Option A** | `stored` — استعمال `vat_amount` المخزَّن كما هو |
| **Option B** | `calculated` — اشتقاقه من `amount_net × vat_rate` |

**البيانات:** §٢ (اتّساق `gross = net + vat`) و§٣ (اتّساق `vat_rate`).

| | A · stored | B · calculated |
|---|---|---|
| **المميزات** | يطابق ما صدر للعميل فعلًا | متّسق رياضيًّا دائمًا |
| **المخاطر** | 🔴 **قد يناقض `net + vat`** (§٢) | 🔴 **قد يناقض الفاتورة الصادرة** · ووحدة `vat_rate` قد تكون مختلطة (15 مقابل 0.15) |
| **الأثر على الأرقام التاريخية** | 🟢 لا شيء | 🔴 **يعيد حساب ضريبة تاريخية** |
| **Migration required?** | ⚠️ يلزم `CHECK` يمنع التناقض مستقبلًا | 🔴 نعم |

**التوصية المحافظة: Option A — `stored`** + إضافة قيد `CHECK` **بعد** تنظيف ما
يرصده §٢.
**ولماذا:** إعادة حساب ضريبة تاريخية تعني **مخالفة مستند صادر**؛ والتناقض يُعالَج
بمنع تكراره لا بإعادة كتابة الماضي.

## ٥. Currency Conversion Policy

| | |
|---|---|
| **Option A** | `reject_mixed` — ⛔ لا جمع عبر العملات، والنتيجة `currency_mismatch` |
| **Option B** | `single_currency_only` — منع إدخال غير عملة الأساس أصلًا |
| **Option C** | `base_currency_conversion` — تحويل إلى عملة أساس |

**البيانات:** §٤-أ و§٤-ب (المشاريع متعدّدة العملات).

| | A | B | C |
|---|---|---|---|
| **المميزات** | 🟢 لا رقم زائف · لا ترحيل | يبسّط كل شيء لاحقًا | تقارير موحَّدة |
| **المخاطر** | تقارير «غير متاحة» لبعض المشاريع | 🔴 يمنع واقعًا قائمًا (صفوف بعملات أخرى) | 🔴 **لا جدول أسعار صرف في القاعدة** ⇒ يلزم بناؤه ومصدره وتاريخه |
| **Migration required?** | ❌ لا | 🔴 نعم | 🔴 نعم — جدول أسعار + سياسة تاريخ |
| **Production verification?** | 🔴 نعم (§٤) | 🔴 نعم | 🔴 نعم |

**التوصية المحافظة: Option A — `reject_mixed`.**
**ولماذا:** لأنّ C **غير قابل للتنفيذ اليوم** (لا أسعار صرف)، وأيّ سعر يُدخَل
ارتجالًا يصير رقمًا يُبنى عليه. و«لا يوجد رقم» أصدق من «رقم بسعر مخترَع».

## ٦. Margin Calculation Policy

| | |
|---|---|
| **Option A** | `net_of_vat` — (إيراد صافٍ − تكلفة صافية) ÷ إيراد صافٍ |
| **Option B** | `gross_including_vat` — بالمبالغ الشاملة |
| **Option C** | `disabled` — ⛔ لا هامش حتّى إشعار آخر |

| | A | B | C |
|---|---|---|---|
| **المميزات** | المعيار المحاسبيّ الشائع · الضريبة ليست إيرادًا | يطابق أرقام الفواتير ظاهريًّا | 🟢 لا رقم يُساء استعماله |
| **المخاطر** | يتطلّب ضريبة متّسقة (§٢) | 🔴 **يضخّم الهامش**: الضريبة ليست ربحًا | تقارير ناقصة |
| **الأثر على التقارير** | `avg_margin_pct` تصير قابلة للحساب | أرقام أعلى من الحقيقة | تبقى `null` بحقّ |

**التوصية المحافظة: Option A — `net_of_vat`**، ⚠️ **ولا تُفعَّل قبل ١ و٢**.
**ولماذا:** لأنّ B **يُنتج رقمًا خاطئًا يبدو صحيحًا** — وهو أخطر من غياب الرقم.

## ٧. Zoho Precedence Policy

| | |
|---|---|
| **Option A** | `zoho_wins` — Zoho يغلب عند التعارض |
| **Option B** | `database_wins` — القاعدة تغلب |
| **Option C** | `flag_conflict` — ⛔ لا يغلب أحد؛ يُرفع التعارض لمراجعة بشرية |

| | A | B | C |
|---|---|---|---|
| **المميزات** | يطابق المستند الرسميّ | استقلال عن تكامل خارجيّ | 🟢 **لا خسارة بيانات ولا كتابة فوق** |
| **المخاطر** | 🔴 مزامنة فاشلة أو قديمة **تكتب فوق** بيانات صحيحة | 🔴 قد يخالف الفاتورة الرسمية | يحتاج عملًا بشريًّا |
| **الأثر على الأرقام التاريخية** | 🔴 قد تتغيّر بلا تدخّل | 🟡 محدود | 🟢 لا شيء |
| **Migration required?** | ⚠️ يلزم ختم قِدَم | ❌ لا | ❌ لا |

**التوصية المحافظة: Option C — `flag_conflict`.**
**ولماذا:** لأنّ A وB كلاهما **يفقد معلومة بصمت**. ورفع التعارض يبقيه مرئيًّا حتّى
يحسمه إنسان — وهو أغلى وقتًا وأرخص خطأً. ⚠️ والعقد يدعم الثلاثة، ⛔ ولا يفترض أحدها.
