# دليل نشر Google Apps Script — Kian Portal Notify Handler

> **الحالة:** 🔴 مطلوب إجراء يدوي منك · مُسجَّل كـ `M-002` في `docs/MANUAL_ACTIONS_QUEUE.md`
>
> **لماذا لا أستطيع تنفيذه:** `clasp` غير مثبَّت، ولا يوجد `~/.clasprc.json`، ولا `.clasp.json` في المستودع.
> والسكربت نفسه يعيش في حساب Google الخاص بك — لا يمكن الوصول إليه من هذا المستودع إطلاقًا.
> **الدليل:** `which clasp` → `clasp not found` · `ls ~/.clasprc.json` → `No such file or directory`.

---

## 1. لماذا هذه الخطوة هي الأهم في مرحلة البريد

بريد كيان **لا يُرسَل من الموقع**. الموقع لا يملك أي مفاتيح بريد إطلاقًا — وهذا قرار تصميم صحيح.
الإرسال الفعلي يحدث داخل Google Apps Script، وهو وحده من يملك صلاحية `MailApp.sendEmail`.

السكربت المنشور حاليًا يحتوي على سطر يعني «أرسل بريدًا لطلبات عروض الأسعار فقط»:

```javascript
if (String(data._type || "") !== "quote") return;   // quotes only
```

وكل إشعارات البوابة تُرسَل بالنوع `portal_notify` — فيخرج السكربت فورًا دون إرسال أي شيء.

**هذا يفسّر بدقّة الملاحظة التي ذكرتَها:** بريد عروض الأسعار والمواعيد ومركز الفرص **يعمل**،
بينما لا يصل أي إشعار من البوابة (المشاريع، العهدة، التأجير، الموارد البشرية). الفرق الوحيد
بينهما هو قيمة `_type`.

### ما الذي أُصلح بالفعل في الكود (ولا يحتاج منك شيئًا)

الطابور والعامل والمُحلِّل سليمة ومُتحقَّق منها:

- الطابور **واحد** — `email_deliveries` (أكّدتُ على الإنتاج عدم وجود طابور ثانٍ).
- منع الإرسال المزدوج مبنيّ: `idempotency_key` + فهرس فريد جزئي.
- **الأهم:** الموقع **لم يعد يزعم النجاح كذبًا**. `lib/server/projectNotify.ts:137` يقرأ جسم رد
  السكربت، وإذا لم يجد معالج `portal_notify` يُرجع `relay_handler_missing` ويُبقي الصفّ في
  الطابور بدل تعليمه «أُرسل». لذلك **لا شيء ضاع** — الرسائل منتظرة في الطابور.

## 2. خطوات النشر (دقيقتان)

المصدر الجاهز للّصق: **`docs/apps_script_portal_notify_HANDLER.gs`** (مكتوب ومراجَع، 176 سطرًا).

1. افتح <https://script.google.com> واختر المشروع الذي يملك رابط الـWeb App المستخدم في الموقع
   (نفس رابط `/exec` الموجود في متغيّر البيئة — **لا تطبع قيمته في أي مكان**).

2. الصق **كامل** محتوى `docs/apps_script_portal_notify_HANDLER.gs` في نهاية `Code.gs`.
   **إضافة فقط — لا تحذف أي شيء موجود.** (هذا ما يحفظ عمل عروض الأسعار والمواعيد.)

3. في دالّة `doPost` الموجودة لديك، أضِف ثلاثة أسطر في **أوّل** الدالّة، مباشرة بعد قراءة البيانات:

   ```javascript
   function doPost(e) {
     var data = JSON.parse(e.postData.contents);

     // ▼▼▼ الإضافة ▼▼▼
     var portal = kianHandlePortalNotify_(data);
     if (portal) return kianJson_(portal);
     // ▲▲▲ نهاية الإضافة ▲▲▲

     // ...بقيّة الكود الحالي كما هو...
   }
   ```

   **موضعها في الأوّل مقصود:** إشعارات البوابة يجب ألّا تُكتب في جدول طلبات عروض الأسعار.

4. **Deploy ← Manage deployments ← عدّل النشر الحالي ← Version: `New version` ← Deploy.**

   ⚠️ **بدون «New version» يبقى الكود القديم يعمل ولن يتغيّر شيء.** هذه أكثر خطوة يُخطأ فيها.

   تأكّد من الإعدادات: `Execute as = Me` · `Who has access = Anyone`.

## 3. التحقّق (لا تكتفِ بأن الخطوات نُفِّذت)

### أ) اختبار داخل محرّر Apps Script
شغّل الدالّة `kianTestPortalNotify_` ثم راجع بريد `info@kianmedia.com`.
النتيجة المتوقَّعة في `Logger`: `{"ok":true,"handler":"portal_notify","sent":1,...}`

### ب) اختبار من البوابة نفسها (الأهم)
من لوحة **«مراقبة الإشعارات»** في البوابة اضغط **«فحص قناة البريد»**.
النتيجة المطلوبة: **القناة تعمل ✓ (handler: portal_notify)**.

إن ظهرت `relay_handler_missing` فالنشر لم يأخذ مفعوله — غالبًا لم تُنشَر نسخة جديدة (الخطوة 4).

### ج) اختبار رحلة حقيقية
ارفع نسخة معاينة لمشروع، ثم تأكّد من وصول البريد للمستلِم المتوقَّع.

## 4. ماذا يحدث للطابور بعد النشر

الصفوف المؤجَّلة بسبب `relay_handler_missing` تبقى `pending` وتُعاد محاولتها تلقائيًا.

⚠️ **قيد مهم يجب أن تعرفه:** الـCron يعمل **مرة واحدة يوميًا**، ونافذة الاسترداد **7 أيام**
(`RECOVERY_WINDOW_HOURS = 168`). أي رسالة أقدم من 7 أيام **لن تُلتقط تلقائيًا** — وهذا مقصود
حتى لا ينفجر إرسال جماعي لبريد قديم.

لذلك بعد النشر:
- الرسائل خلال آخر 7 أيام: **تُرسَل تلقائيًا** في أول تشغيل للـCron (أو فورًا عبر «معالجة الآن»).
- الرسائل الأقدم من 7 أيام: تحتاج قرارًا إداريًا واعيًا من لوحة الإشعارات.
  راجعها أولًا — قد يكون بعضها لم يعد ذا معنى (قرار عميل قديم، تنبيه انتهى).

> 🐞 **عيب مُكتشَف قيد الإصلاح في P1:** دالّة `pc_email_retry` تُعيد الصفّ إلى `pending` وتصفّر
> المحاولات، لكنها **لا تستطيع تغيير `created_at`**. فإذا أعدتَ محاولة صفّ أقدم من 7 أيام، سيبدو
> أن العملية نجحت بينما يبقى الصفّ خارج نافذة الـCron ولا يُرسَل أبدًا. الإصلاح ضمن P1 — وحتى
> يُطبَّق، استخدم زرّ **«معالجة الآن»** على الصفّ المحدَّد (يعمل بمعرّف الصفّ مباشرة ويتجاوز النافذة).

## 5. الأمان والحدود

| البند | التفصيل |
|---|---|
| المفاتيح | لا مفاتيح بريد في المستودع إطلاقًا — السكربت وحده يملك الصلاحية. **لا تضع قيمة رابط الـWeb App في أي ملف داخل المستودع.** |
| العزل | كل شيء داخل `try/catch`: فشل البريد لا يُفشِل كتابة الجدول أبدًا. |
| الخصوصية | رسالة منفصلة لكل مستلِم — لا تُكشف العناوين بين المستلِمين. |
| الصدق | يردّ JSON صريحًا، فيميّز الموقع «وصلت فعلًا» من «السكربت لم يفهمها». |
| الحصّة | **100 رسالة/يوم** لحساب Gmail عادي · **1500** لحساب Google Workspace. التجاوز يُسجَّل كخطأ صريح (لا فشل صامت). |

## 6. التراجع

احذف الأسطر الثلاثة من `doPost` وانشر نسخة جديدة. يعود السلوك السابق تمامًا
(بريد عروض الأسعار يعمل، وإشعارات البوابة تعود للانتظار في الطابور — **دون ضياع**).
